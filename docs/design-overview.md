## 1. 位置づけ

```
[運用者・テナントの利用者のブラウザ] ─Cloudflare Access─> cloudflared ─HTTP─> aka-ossbss ── PostgreSQL（台帳・ジョブ・課金レコード・監査ログ）
                                                                               │      KEK（ファイル。一括投入の待ちのファイル）
                                                                               └─mTLS─> aka-provisioner ─> aka-vecgen / aka-radius / radsec-ca / エッジ
```

- テナント・利用者・権限の境界は aka-ossbss だけが持つ（下流と aka-provisioner は全権の管理クライアントとして扱う。もとの実装のまま）。
- MVP では、もとの実装の画面に加えて、管理面の業務の処理を受け持つ。
  - **加入者の台帳**（概要 §6.4）: 一覧・件数・絞り込みと一括投入の前の確かめを台帳で行い、下流と定期的に突き合わせる。
  - **一括投入と一括の物理削除のジョブ**（概要 §10）。
  - **課金レコード**（`charging-records.md`）: 状態の事実の記録、利用の集計の取り込み、締め、PGP で暗号化したファイル。
  - **RadSec の受け口の管理**（radsec-edge の管理モード）: エッジの台帳、テナントの配置、AP・グループ・持ち込みの CA、中央の整合のループ。
- 加入者のデータ（鍵、SQN、状態、認可ポリシー）の正本は下流（aka-vecgen、aka-radius）のまま。台帳はその写し（概要 §6.4）。テナントと RadSec の望む状態の正本は aka-ossbss（radsec-edge §6）。

## 4. 技術方針

- もとの実装の方針を引き継ぐ。Go 1.27.3、標準ライブラリを優先、外部依存は `github.com/jackc/pgx/v5`。画面は Go + htmx + daisyUI（JavaScript は書かない）。
- 課金レコードの PGP の暗号化のために `github.com/ProtonMail/go-crypto` を足す（`charging-records.md` §8.3）。
- module パスは `github.com/oyaguma3/aka-ossbss`、コマンド名は `aka-ossbss`、環境変数の接頭辞はもとの `OSSBSS_` のまま（§20 の F1）。
- 認証はもとの実装のまま（Cloudflare Access の JWT の検証、メールアドレスでアカウントを引く、最初のシステム管理者、開発用の設定）。
- 時間のかかる処理（一括投入、突き合わせ、利用の集計の取り込み、締め、中央の整合のループ）は、aka-ossbss のプロセスの中のジョブとして動かす（§20 の F11）。
- ブランチは `main` に直接コミットする（もとの実装と同じ）。

## 6. テナント

| 項目 | 内容 |
|---|---|
| `id` | 番号（PostgreSQL の identity。使い回さない）。刻印の値になる（決定事項 7） |
| `name` | 表示名 |
| `slug` | RadSec の名前に使う（radsec-edge §8.1 の規則）。RadSec を有効にするときに決め、変えない |
| `external_customer_id` | 外部の顧客番号（課金レコードの決定事項 11） |
| RadSec の設定 | ポート（全体で一意）、送信元の範囲（任意）、配置（エッジとスロット） |

- すべての IMSI はどれか 1 つのテナントに属する。もとの実装の「テナントなし」はなくす（§20 の F2）。外形監視の試験用の SIM も、専用のテナントに属させる（概要 §14）。
- 加入者・AP・配置が残っているテナントは削除できない。削除したテナントの行は残し（削除済みの印）、ID と slug を使い回さない。

## 7. 加入者の台帳

### 7.1 項目

| 項目 | 内容 |
|---|---|
| `imsi` | 主キー |
| `tenant_id` | 所属のテナント（必須） |
| `vecgen_present`、`vecgen_state` | vecgen 側の有無と状態 |
| `radius_present`、`radius_state`、`radius_source_id` | radius 側の有無と状態、取得先 ID |
| `external_line_id` | 回線の外部の番号（任意。課金レコードの決定事項 11） |
| `registered_at`、`registered_by` | 最初の登録の日時と操作者 |
| `deleted_at` | 削除済みの印（両側とも物理削除したとき） |
| `check_needed` | 下流の結果が分からなかった操作の印（§7.2） |

### 7.2 書き方

- 台帳は、aka-provisioner を通した操作が成功（2xx）したときだけ書く。課金レコードの状態の事実（`charging_events`）と同じトランザクションで書く（`charging-records.md` §5.1）。
- 下流の結果が分からない（503・タイムアウト・502）ときは、台帳を変えずに `check_needed` を立て、その IMSI だけをすぐに一括取得で確かめて直す（直したときは状態の事実を補いとして記録する）。画面には「結果を確かめています」と出す（§20 の F3）。
- 同じ IMSI の操作は、台帳の行のロック（`SELECT … FOR UPDATE`）で順に行う（画面と一括投入のジョブが同じ IMSI を同時に触らないように）。
- 削除済みの IMSI を登録し直すときは、警告を出し、D の承認（画面での確認と理由）を要る。承認は監査ログに残す（決定事項 2）。

### 7.3 一覧と表示

- 一覧・件数・絞り込み（テナント、状態、取得先、食い違い、削除済み）は台帳で行う（もとの設計概要 §18.3）。1 ページは 50 件。
- 一覧の表示の項目のうち、台帳にないもの（AMF・SQN・ルールの件数）は、そのページの IMSI を aka-vecgen・aka-radius の一括取得で読む（2 回の呼び出し）。
- 詳細の画面は、vecgen 側と radius 側を並べて出し、状態の食い違い（例: vecgen は Active、radius は Inactive）を示す（概要 §6.3）。
- ダッシュボードの件数（テナントごとの加入者、状態ごとの数）は台帳から数える。

## 8. 加入者の操作

- vecgen 側と radius 側を別々に操作する（aka-provisioner の決定事項 1）。1 つの画面の操作で両側を続けて呼ぶとき（例: 状態を両方 Inactive にする）は、1 つずつ呼び、片方だけ失敗したら、その結果を画面に出す（取り消さない）。
- 個別の登録は、vecgen 側（D。鍵を入力。Ki・OPc はフォームから aka-provisioner に送るだけで、DB・ログ・監査ログに残さない）と radius 側（C・D）の別々のフォームにする。
- vecgen 側の許可クライアントは aka-vecgen の AV クライアントの一覧（`GET /vecgen/clients`）から選ぶ。radius 側の取得先は aka-radius の登録簿（`GET /radius/sources`）から選ぶ。

### 8.1 認可ポリシーの編集

- ルールの項目は aka-radius §8.2 のとおり（テナント、NAS-Identifier、SSID、VLAN、Session-Timeout）。
- ルールのテナントは、台帳の所属のテナントに限る（画面ではテナントを選ばせず、所属のテナントを入れる。§20 の F4）。
- NAS-Identifier は、登録した AP・グループの NAS-Identifier から選ぶか、自由に書ける（持ち込みの CA の AP やグループの AP は、AP が名乗る値がそのまま届くため）。`*` も A・B・C・D が使える。刻印でテナントの中に限られるので、他のテナントの AP に当たることはない（radsec-edge §19 の 9 の「`*` は C・D だけ」と「自分のテナントの AP だけを選べる」を、刻印を前提に改める。§20 の F4）。
- 所属のテナントの付け替え（D）は、radius 側のルールのテナントも書き換える（aka-radius の `PATCH` の後に台帳を書く）。

## 9. 突き合わせ

- 毎日（案: 日本時間 4 時）と、D の画面からの手での実行で、台帳と下流を突き合わせる（§20 の F6）。
- aka-vecgen と aka-radius の一覧（`GET /subscribers`、500 件ずつ。20 万件でそれぞれ 400 回）を全部たどり、台帳と比べる。

| ずれ | 扱い |
|---|---|
| 台帳にあって下流にない | 台帳を下流に合わせる（その側を「なし」に）。状態の事実を補いとして記録する |
| 状態・取得先が違う | 台帳を下流に合わせる。状態の事実を補いとして記録する |
| 下流にあって台帳にない | 自動では直さず、D の画面に出す。D がテナントを選んで台帳に取り込むか、下流から削除する |

- 下流が正本なので、台帳の側を直す。直したことは突き合わせの結果（`reconcile_findings`）と監査ログに残し、D の画面に出す。
- 突き合わせの間も画面と一括投入は止めない。突き合わせの途中で変わった IMSI は、台帳の更新の時刻で見分けて次の回に回す。

## 10. 一括投入と一括の物理削除

概要 §10 のとおり。本書では作りを書く。

### 10.1 ジョブ

| ジョブ | 一律に選ぶもの | CSV の列（ヘッダーを固定） |
|---|---|---|
| vecgen への登録 | テナント、状態、許可クライアント、SQN の方式 | `imsi,ki,opc,amf,sqn` |
| radius への登録 | テナント、状態、認可ポリシー（ルールの組。テナントは選んだテナント）、取得先 | `imsi` |
| vecgen からの物理削除 | — | `imsi` |
| radius からの物理削除 | — | `imsi` |

- CSV は UTF-8、ヘッダー行あり、1 回 10,000 行まで、ファイルは 8 MiB まで（もとの設計概要 §18.5）。
- アップロードのときに、ファイルを KEK（`OSSBSS_KEK_FILE`。AES-256-GCM。AAD は `aka-ossbss/bulk-job/<ID>`）で暗号化して `bulk_jobs` に置く。完了・中断・取り消しのときに消す（概要 §10.2・§12.1）。平文のファイルはディスクに書かない。
- 待ち行列は対象（vecgen / radius）ごとに 1 本で、それぞれ同時に 1 つのジョブを動かす。

### 10.2 検証の段

全行を先に確かめ、1 行でも不合格があれば何も投入しない（行番号つきで誤りを出す）。

- 形式（IMSI、16 進の桁数、ヘッダー）、ファイルの中の IMSI の重複、件数の上限。
- 台帳での所属の食い違い（台帳に別のテナントで登録されている IMSI）。
- 削除の対象が Active でないこと（台帳の状態で確かめ、実行の段の 409 でも数える）。
- 削除済みの IMSI の数を出し、登録し直すなら D が承認する（チェックと理由。承認しなければ、その行を除いて進めるか、ジョブを取り消す）。
- 台帳に既にある IMSI は「既にある」として件数を先に出す。

### 10.3 実行の段

- 同時に 5 件ずつ aka-provisioner を呼ぶ。行の `Idempotency-Key` はジョブの ID と IMSI から作り、`X-Trace-ID` にジョブの ID を入れる（概要 §10.3・§10.4）。
- 成功のたびに台帳と状態の事実を書く。409（既にある）は「既にある」、削除の 404 は「ない」として数える。
- 下流に接続できない誤りが 10 件続いたら自動で中断する。
- 1 万件を 30 分以内（毎秒 5.6 件）。1 件 200 ミリ秒でも 5 並列で約 7 分の見込み（規模の試験で確かめる）。
- aka-ossbss が止まったら、動いていたジョブは「中断」（起動のときに印を付ける）。待っていたジョブは残り、起動の後に続けて動かす。

### 10.4 中断と報告

- D はジョブを中断できる（処理中の行を終えてから止める。再開はしない。同じファイルを投入し直せば残りだけが処理される）。
- ダッシュボードに進み具合・完了数・失敗数・待ちのジョブを出す（htmx の定期の読み込み）。
- 結果（件数、失敗した行と未処理の行の一覧。鍵は含めない）を残し、CSV でも取り出せる。監査ログは、ジョブの開始・終了・中断と、行ごとの操作（ジョブの ID つき）。

## 11. セッション

- A・B は、aka-radius の `GET /sessions?tenantId=<自分のテナント>` で見る（刻印のテナントで絞る。もとの実装の「新しい 1000 件を取って所属で絞る」をやめる）。
- C・D は、テナントや IMSI（複数）で絞って見る。
- 刻印のテナントは「その接続がどのテナントのネットワークから来たか」で、台帳の所属と違うことがある（ルールで他のテナントを許していないので、通常は同じ）。
- 開始の時刻の新しい順の一覧は、aka-radius のセッションの開始時刻の索引（概要 §19 の 5。20,000 件で測ってから決める）しだいで足す。

段階 3-1 で決めたこと（2026-10-30。aka-mvpset の概要 §18.7 の段階 3 の進め方 Q1〜Q10 と、確認事項 W1〜W12 はすべて推奨案で合意）:

- W1: 1 つの手順にし、中ではコミットを分けた（スキーマと台帳、aka-provisioner v2 のクライアント、画面、なくす画面、compose と CI、本書）。画面は手元の開発用の設定（`OSSBSS_ADDR=127.0.0.1:18446`、`OSSBSS_DEV_USER_EMAIL`）で、aka-provisioner の `scripts/contract.sh` で起動した本物の aka-provisioner・aka-vecgen・aka-radius につなぎ、役割 A〜D ごとに確かめた（playwright-cli）。Cloudflare を通すのは段階 3 の終わり。画面仕様（`docs/screen-spec.md`）と運用ガイドの書き直しは 3-5。
- W2: スキーマは MVP の起点 `internal/db/migrations/0001_mvp.sql`（PoC の `0001_init.sql` を置き換えた）。表は `tenants`（`external_customer_id`・`deleted_at` を足し、名前は削除していないテナントの中で一意）、`accounts`（もとのまま）、`subscribers`（台帳。§7.1。有無と状態・取得先の組み合わせ、削除済みならどちらの側もないことを CHECK で守る）、`charging_events`、`audit_log`（`job_id` を足した）。PoC のスキーマ（`subscriber_tenants`）の DB では、移行を断って起動しない（`db.ErrPoCSchema`。新しい DB で始める）。テナントの削除は `deleted_at` を付けて行を残す（加入者（削除済みを除く）とアカウントが残っていれば断る）。
- W3: `charging_events` は台帳を書くのと同じトランザクションで書く（`db.WithSubscriber` の `Apply`、テナントの作成・名前の変更・削除）。`from_val`・`to_val` は、状態の事実では状態（ないときは空）、付け替えではテナントの ID、テナントの事実では名前。`tenant_id` は付け替えでは移った先。月次の計算・締め・ファイルは 3-4。
