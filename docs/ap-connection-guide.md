# AP の接続の手順書

- 対象: テナント管理者と、AP の設定を担当する人。
- 内容: RadSec に対応した AP を、このサービスの受け口につなぐ一般的な手順。製品ごとの画面の操作は書かない（製品の資料を見る。製品ごとの導入ガイドは、受入試験の後に作る）。
- 関連: [画面仕様](screen-spec.md) §12、[運用ガイド](operation-guide.md) 14 章（運用担当の手順）

## 1. RadSec のつなぎ方

RadSec は、RADIUS を TLS（TCP）で運ぶ方式である。AP とサービスの受け口（エッジ）が、お互いの証明書を確かめてからつなぐ。

```
[AP] ── RadSec（TLS。AP のクライアント証明書とサーバー証明書の両方を確かめる） ──> [エッジ] ──> 認証のサーバー
```

- テナントごとに、受け口のポートとサーバーの名前が決まっている。
- サーバーの名前は置いたスロットごとにあり（`primary`・`secondary`・`tertiary`）、エッジが 1 台止まっても、AP は別のサーバーへつなぎ替えられる。
- RADIUS のシークレットは TLS の中で使う決まった値（`radsec`）で、秘密の値ではない。守りは証明書で行う。

## 2. AP の条件

次を満たすことを、最初に確かめる。

| 条件 | 内容 |
|---|---|
| RadSec（RADIUS over TLS）に対応している | RADIUS のサーバーの設定に TLS の選択がある |
| ポートを変えられる | **2083 番以外**のテナントのポートを設定できること（できない AP は、今の作りでは収容できない） |
| クライアント証明書を入れられる | 証明書と秘密鍵を AP（または AP を管理する仕組み）に入れられること |
| サーバーCA を入れられる | サーバー証明書を確かめる CA を設定できること |
| 複数のサーバーを設定できる | 予備のサーバーを設定できることが望ましい |
| AP から外へつなげる | AP からサーバーの名前とポートへ、TCP で外向きに接続できること |

AP を置く拠点の IP アドレスが固定なら、送信元の範囲で絞れる（運用担当に頼む。範囲の外からの接続は TLS に応じない）。

## 3. 登録のしかたを選ぶ

| 種類 | 使うとき | 証明書 | AP の見分け方（NAS-Identifier） |
|---|---|---|---|
| AP | AP 1 台ごとに証明書を入れられるとき。**できるならこれを選ぶ** | AP 1 台に 1 枚 | エッジが `<slug>-<AP の名前>` に置き換える |
| グループ | 証明書と鍵を 1 組だけ入れて AP のまとまりで共有するとき | まとまりに 1 枚 | AP が送った値をそのまま通す。送らなければ `<slug>-<グループの名前>` を補う |
| 持ち込みの CA | AP の業者の CA が AP ごとに証明書を出すとき | 業者の CA が発行する | AP が送った値をそのまま通す |

- 持ち込みの CA の登録はシステム管理者が行う。業者の組織ごとの CA に限る（全顧客で共通の CA は受けない）。使いたいときは運用担当に相談する。
- グループは、鍵が AP の全台や管理の仕組みに置かれるので、漏れる経路が AP ごとの証明書より多い。AP を 1 台ずつ見分けるために、AP の名前や MAC アドレスなどを NAS-Identifier に送るよう、製品で設定する。
- 認可ポリシーのルールの NAS-Identifier には、ここで決まる値を書く（登録した AP とグループは候補に出る）。

## 4. 手順

### 4.1 鍵と CSR を作る

鍵は手元で作り、外に出さない。サービスは鍵を受け取らず、作りもしない。

```bash
openssl req -new -newkey ec -pkeyopt ec_paramgen_curve:prime256v1 -nodes -keyout ap.key -out ap.csr -subj "/CN=ap"
```

- 受け付ける鍵は ECDSA P-256・P-384、RSA 2048〜4096 ビット。AP が受け付ける種類を選ぶ（Ed25519 は使えない）。RSA を使うときは `-newkey rsa:2048` にする。
- CSR の Subject（`/CN=ap`）は使わない。証明書の名前はサービスが決める（CN は `<slug>-<名前>`、SAN は URI）ので、何を書いてもよい。
- `-nodes` は鍵を暗号化しない指定である。`ap.key` は権限を絞って置く（`chmod 600 ap.key`）。

### 4.2 登録して証明書を受け取る

1. 「RadSec」から「AP・グループ」を開く。
2. 名前と種類を選び（グループなら用途も。用途は表示のためのもので、動作は変わらない）、`ap.csr` の中身を貼り付けて「登録して発行する」を押す。名前は小文字の英数字と `-` で 32 文字まで。`probe` は使えない。
3. AP の詳細の「証明書」で証明書（`.pem`）を、「接続の案内」の「取り出す」でサーバーCA の証明書を取り出す。

### 4.3 反映する

**登録しただけではつながらない。** 「RadSec」の画面で「反映する」を押す。

- 配置したエッジに 1 台ずつ順に反映する。AP やグループを増やすと、そのエッジの AP の接続がいったん切れ、AP は予備のサーバーへつなぎ替える。
- 何件足しても再起動は 1 回で済むので、まとめて登録してから押す。
- 画面は自動で変わらない。開き直して「反映済み」になったことを確かめる。「反映に失敗しました」と出たら「やり直す」を押す。繰り返すときは運用担当に連絡する。

### 4.4 AP に設定する

AP の詳細の「接続の案内」の値を設定する。

| 項目 | 値 |
|---|---|
| サーバーの名前 | 「RadSec サーバーの名前」のすべて（`primary.<slug>.<ドメイン>` など。上から順に優先する） |
| ポート | 「ポート」の値 |
| シークレット | `radsec` |
| クライアント証明書と秘密鍵 | 4.2 の証明書と、4.1 の `ap.key` |
| サーバーCA | 4.2 のサーバーCA の証明書 |

名前の DNS の登録は運用担当が行う。名前が引けないときは運用担当に連絡する。

### 4.5 つながったことを確かめる

「AP・グループ」の「接続の状態」で確かめる（1 分ほど遅れて変わる）。

AP を設定する前に、手元から試すこともできる（`Verify return code: 0 (ok)` が出ればサーバー証明書は正しく確かめられている）。

```bash
openssl s_client -connect primary.<slug>.<ドメイン>:<ポート> -CAfile radsec-server-ca.pem -cert <証明書>.pem -key ap.key </dev/null
```

## 5. 更新と失効

| したいこと | 手順 |
|---|---|
| 証明書を更新する | 1. 新しい鍵と CSR を作る。2. AP の詳細の「証明書の更新」に貼り付けて発行する（同じ名前なのでエッジの設定は変わらず、反映は要らない）。3. AP に入れ替える。4. 古い証明書を失効させる。新旧が両方有効な間はどちらでもつながる |
| 期限を知る | 「AP・グループ」の「証明書の期限」。残り 30 日を切ると「期限が近い」と出る。証明書の有効期間は 2 年で、更新は自動では行われない |
| 鍵が漏れた | 新しい鍵で発行し直して AP に入れ替え、古い証明書を鍵の漏えいとして失効させる。すぐ止めたいときは先に失効させる（その AP はつながらなくなる） |
| AP をやめる | AP の詳細の「削除する」。証明書を失効させてから消す |

失効は、各エッジに自動で伝える。

## 6. つながらないとき

| 症状 | 確かめること |
|---|---|
| 「接続の状態」に記録がない | 反映したか（4.3）。AP の設定のポート（2083 のままになっていないか）。サーバーの名前が引けるか。AP から外へ TCP でつなげるか。送信元の範囲を設定していれば、AP の IP アドレスが範囲に入っているか |
| 「最後の拒否」に時刻が出る | エッジまで届いたが断られている。証明書が期限切れか失効していないか、登録した AP の証明書を入れているか |
| `openssl s_client` で `Verify return code` が 0 でない | サーバーCA を取り違えていないか。手元の時刻が正しいか |
| つながるが認証で断られる | 認可ポリシーのルールの NAS-Identifier と SSID（3 章） |
| 「反映に失敗しました」のまま | 「やり直す」を押す。繰り返すなら運用担当に連絡する |
| 接続がときどき切れる | 反映のときと、エッジの更新のときは切れる。予備のサーバーを設定しているか |
