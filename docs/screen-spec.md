# aka-ossbss 画面仕様

- 状態: ステップ 4 の画面（加入者、認可ポリシー、停止・再開、RADIUSクライアント、セッション。§1〜§5）と、ステップ 5 の画面（ダッシュボード、所属の付け替えと点検、テナント、アカウント、操作の記録、監査ログ。§6〜§11）（2026-10-11）。
- 元にした決定: 設計概要 §6（役割と権限）、§7（テナントと所属）、§8（停止）、§9（画面の概要）、§10（provisioner との連携）、§13（監査ログ）、§17.4・§17.5（ステップ 4・5 の確認事項）。
- 手本: 既存の BFF（web-gui-for-eapaka-radius）の `docs/screen-spec.md` の §6〜§9、§11。

役割の呼び名は、A テナントユーザー、B テナント管理者、C 運用担当、D システム管理者（設計概要 §6.1）。

## 1. 共通

### 1.1 画面の作り

- 見た目は daisyUI。テーマはブラウザの設定（ライト / ダーク）に従う。JavaScript は書かず、画面の一部の差し替えは htmx で行う。
- ナビゲーションに「ダッシュボード」「加入者」「RADIUSクライアント」「セッション」（全員）、「テナント」（D）、「アカウント」（B・D）、「操作の記録」（C・D）、「監査ログ」（B・C・D）を出す。開いている画面の項目を強調する。
- 画面の上部に、成功の文（緑）とエラーの文（赤）を出す。入力の誤りは各項目の下にも出す。

### 1.2 権限とテナントの範囲

- 権限は設計概要 §6.2 の表のとおり。画面に出さないだけでなく、要求を受けたときにも必ず判定する（`authz.Allowed`）。
- A・B が扱えるのは、自分のテナントに属する加入者・RADIUSクライアントだけ。テナントなしのものは C・D だけが扱う。
- 範囲の外のもの（他のテナントのもの、テナントなし）の IMSI・ID を A・B が開いたり送ったりしたときは、存在しないときと同じ 404 を返す（「加入者 … は見つかりません（このテナントに属していないか、登録されていません）。」）。存在の有無を漏らさないため（§17.4 の 2）。
- 範囲の中のものでも、役割にない操作（A の認可ポリシーの編集、B の加入者の削除など）は 403「この操作の権限がありません。」。
- A・B の画面には、鍵の置き場所・AMF・SQN・2 つのノードの食い違い（`issues`）・鍵の有無を出さない。停止の状態は出す。

### 1.3 所属（テナント）の表示

- C・D の一覧と詳細には、所属のテナントの名前を出す。所属の記録がなければ「テナントなし」と出す。
- 本BFF に所属の記録があるのに provisioner にないもの（本BFF の外で削除されたもの）は、「下流にない」のバッジを付けて出す。記録を消すのは D（ステップ 5）。

### 1.4 確認ダイアログ

- 停止・再開、削除、既定の動作が allow のときの保存・登録の前に、確認ダイアログを出す（daisyUI の `modal`、`<dialog>`）。
- ダイアログは HTML の Invoker Commands（`<button command="show-modal" commandfor="…">`）で開き、「やめる」とダイアログの外を押すと閉じる（`<form method="dialog">`）。確認のボタンは、送るフォームを `form` 属性で指す（§17.4 の 4）。

### 1.5 二重送信の防止（Idempotency-Key）

- provisioner への書き込みのフォーム（加入者の登録・変更・削除、停止・再開、認可ポリシーの保存、RADIUSクライアントの登録・変更・削除）には、表示のたびに作るキー（隠し項目）を持たせ、`Idempotency-Key` として送る（§17.4 の 7）。同じフォームを送り直しても、provisioner は最初の結果を返す。
- provisioner に届かなかった（接続できない・タイムアウト）ときは同じキーを残す。provisioner が断った（4xx）ときは新しいキーにする（入力を直して送ると内容が変わるため）。
- 停止・再開のフォームのキーは `status_idem`、それ以外は `idem` という名前にする（認可ポリシーの画面の停止・再開は、編集中のフォームも一緒に送るため、名前を分ける）。

### 1.6 provisioner のエラー

既存の BFF の §11.1 と同じ文を使う。ただし、A・B には操作の記録や設定の名前を出さない（見られない・扱えないため）。

| 場合 | C・D | A・B |
|---|---|---|
| provisioner に接続できない | 原因の見当（設定 `OSSBSS_PROVISIONER_*`、`PROVISIONER_ADMIN_CLIENTS` 等） | 「provisioner に接続できません。しばらくしてからもう一度操作してください。続く場合は運用担当に連絡してください。」 |
| 下流に接続できない（503） | 「provisioner から aka-vecgen に接続できません。（途中まで行った変更は元に戻しました。）ダッシュボードで接続の状態を確かめてください。」 | 同じ文の後半を「しばらくしてからもう一度操作してください。続く場合は運用担当に連絡してください。」にする |
| 同じ IMSI の操作が処理中（409） | 「同じ IMSI の操作が処理中です。少し待ってから、もう一度操作してください。」 | 同じ |
| 同じ IMSI に完了していない操作がある（409） | 「同じ IMSI に完了していない操作が残っています。「操作の記録」で、その操作をやり直すか閉じてから、もう一度操作してください。」と操作の記録の ID | 「同じ IMSI に完了していない操作が残っています。運用担当に対応を依頼してください。」 |
| 途中で失敗し、元に戻せなかった（500） | 「… への操作が途中で失敗し、元に戻せませんでした。provisioner が後で自動でやり直します。「操作の記録」で状況を確かめてください。」と操作の記録の ID | 「… への操作が途中で失敗しました。provisioner が後で自動でやり直します。続く場合は運用担当に連絡してください。」 |
| 送信の内容が前回と違う（422） | 「送信の内容が前回と違います。画面を開き直してから、もう一度操作してください。」 | 同じ |

- 操作の記録の ID は、操作の記録の画面（§10）へのリンクにする（C・D だけ）。
- 書き込みのエラーの後は、可能なら対象を読み直して画面を出し直す（入力は残す。秘密の値は残さない）。読み直せなければエラーの画面に元の失敗の文を出す。

### 1.7 監査ログ

- 本BFF の監査ログに、成功した変更操作と秘密の値の表示を残す（§17.4 の 6）。操作者のメールアドレス・役割、対象のテナント（テナントなしは空）、操作、対象（IMSI、RADIUSクライアントは `#ID`）、内容（変えた項目の名前など。秘密の値は入れない）、トレースID、接続元。
- 失敗した操作は記録しない（provisioner と下流の監査ログ、本BFF のアクセスログでトレースID から追える）。
- provisioner の操作は成功し、監査ログの書き込みだけが失敗したときは、画面には成功を出し、ERROR のログを出す。
- 閲覧の画面は §11。

| 操作（`action`） | 記録するとき |
|---|---|
| `subscriber.create` | 加入者の登録。内容: 鍵の置き場所、AMF、SQN、認可ポリシーの既定の動作 |
| `subscriber.update` | 加入者の変更（Ki / OPc / AMF / SQN 等）。内容: 鍵の置き場所、変えた項目の名前 |
| `subscriber.delete` | 加入者の削除 |
| `subscriber.keys.read` | Ki / OPc の表示 |
| `policy.put` | 認可ポリシーの保存。内容: 作成か、既定の動作、ルールの件数 |
| `policy.suspend` / `policy.resume` | 加入者の停止 / 再開 |
| `client.create` | RADIUSクライアントの登録。内容: IP アドレス、名前、ベンダー |
| `client.update` | RADIUSクライアントの変更。内容: 変えた項目の名前（IP アドレスは変更前と変更後） |
| `client.delete` | RADIUSクライアントの削除 |
| `client.secret.read` | 共有シークレットの表示 |
| `assignment.update` | 所属の付け替え（§7）。内容: 種類（加入者 / RADIUSクライアント）、変更前と変更後のテナント。移動元と移動先が別のテナントなら、それぞれのテナントに 1 行ずつ書く（テナントなしの側には書かない） |
| `assignment.delete` | 下流にない所属の記録の削除（§7.2）。対象のテナントは記録のテナント |
| `tenant.create` / `tenant.update` / `tenant.delete` | テナントの作成・名前の変更・削除。対象のテナントはそのテナント |
| `account.create` / `account.update` / `account.disable` / `account.enable` / `account.delete` | アカウントの操作。対象はメールアドレス、対象のテナントはアカウントのテナント（役割・テナントの変更は、変更前と変更後のテナントにそれぞれ 1 行） |
| `operation.retry` / `operation.dismiss` | 操作の記録のやり直し・閉じる。対象は操作の ID |

## 2. 加入者

### 2.1 一覧（`/subscribers`）

- 全員が使える。IMSI の前方一致（15 桁までの数字）で検索できる。
- A・B: 自分のテナントの所属の記録を IMSI の順に 20 件ずつ読み、各 IMSI を provisioner から並行して（同時に 5 件まで）取得する（設計概要 §7.1）。見出しに件数（所属の記録の数）を出す。
- C・D: テナントの絞り込みを出す（「すべて」「テナントなし」と各テナント）。
  - すべて: provisioner の一覧を 50 件ずつ出し、各行にテナントの名前を添える。
  - テナントを選んだとき: A・B と同じ作り（所属の記録から 20 件ずつ）。
  - テナントなし: provisioner の一覧を 500 件ずつ読み、所属の記録のないものだけを残す。50 件たまるか、1 回の表示で 5,000 件を調べたところで止める。途中で止めたときは「5,000 件を調べました（IMSI … まで）。」と「続きを探す」を出す（§17.4 の 8）。
- ページは「次のページ」「先頭へ」で移る（続きの位置は IMSI）。
- 項目:

| 項目 | A・B | C・D |
|---|---|---|
| IMSI（詳細へのリンク） | ○ | ○ |
| テナント | - | ○ |
| 鍵の置き場所 | - | ○ |
| SQN・AMF（鍵がなければ「鍵なし」） | - | ○ |
| 認可ポリシー（既定の動作とルールの件数。なければ「なし」） | ○ | ○ |
| 状態（「利用中」、バッジ「停止中」、不明な値は「不明な状態（値）」。認可ポリシーがなければ「-」） | ○ | ○ |
| 食い違い（名前） | - | ○ |

- 所属の記録があるのに provisioner にない IMSI は、「下流にない」のバッジを出す。provisioner から取得できなかった行は「取得できませんでした」と出し、画面の上部にエラーの文を出す。
- C・D の一覧では、鍵を本PoCに置く加入者について aka-vecgen 側を調べないことを注記する（既存の BFF と同じ）。
- C・D には「加入者の登録」のボタンを出す。
- 削除の後は「加入者 … を削除しました（認可ポリシーも削除しました）。」

### 2.2 登録（`/subscribers/new`）

- C・D だけ。
- 入力: 所属のテナント（必須の選択。「テナントなし」か各テナント。うっかりテナントなしにしないよう、既定は「選んでください」）、IMSI（15 桁）、Ki、OPc（16 進 32 桁）、AMF（16 進 4 桁、既定 8000）、SQN（16 進 12 桁、既定 000000000000）、認可ポリシーの既定の動作（deny / allow。既定 deny）。16 進は大文字でもよく、小文字にして送る。
- 鍵の置き場所は選ばせず、provisioner の PLMN マップ（例「00102 → aka-vecgen。それ以外の PLMN は本PoC」）を説明に出す。
- 既定の動作を切り替えるとフォームを描き直す（`POST /subscribers/new/form`。入力は残し、provisioner には送らない）。allow のときは、登録の前に確認ダイアログ「認可ポリシーの既定の動作が allow です。どのルールにも一致しない接続も許可します。登録してよろしいですか？」を出す。
- 認可ポリシーはルールなしで加入者と一緒に作る。ルールは登録後に認可ポリシーの画面で編集する。
- 登録したら、所属の記録を書き（テナントなしなら記録を消す。本BFF の外で削除されて残っていた記録を消すため）、詳細へ移動して「加入者を登録しました（認可ポリシーも作りました）。」を出す。
- 所属の記録の書き込みに失敗したときは、詳細に「加入者を登録しましたが、所属の記録に失敗しました（テナントなしになっています）。システム管理者に所属の付け替えを依頼してください。」を出す（§17.4 の 3）。

| 誤り | 表示 |
|---|---|
| 形式 | 項目ごとに「IMSI は 15 桁の数字で入力してください。」「Ki は 16 進 32 桁で入力してください。」など。テナントは「所属のテナントを選んでください。」 |
| 選んだテナントがない（他の操作で削除された） | 「選んだテナントはありません。画面を開き直してください。」 |
| 既にある | 409「その IMSI は既に登録されています（本PoCの鍵、認可ポリシー）（本PoCの Admin TUI など、他の操作で登録された場合もあります）。」のように、あった場所を出す |

### 2.3 詳細（`/subscribers/{imsi}`）

- 全員が使える（A・B は自分のテナントのものだけ）。
- 全員に出す項目: IMSI、認可ポリシーの概要（既定の動作、ルールの一覧（NAS-ID、許可する SSID、VLAN ID、Session-Timeout）。なければ「なし」）、状態と停止・再開のボタン（§2.4）、セッションへのリンク。
- B・C・D には、認可ポリシーの編集画面へのリンク（なければ「作成する」）を出す。
- C・D に出す項目: テナント、鍵の置き場所、SQN、AMF、登録日時（aka-vecgen の加入者は、SQN の増加タイプ、平文HTTP での払い出し、許可するクライアントID、変更日時も）。鍵がなければ「なし」。食い違いがあれば、先頭に名前と説明・対処（既存の BFF §11.4 の表）を出す。
- C・D には、鍵があるとき Ki / OPc の表示のボタンを出す（押したときだけ取得する。表示したことは provisioner・下流と本BFF の監査ログに残る）。
- C には「Ki / OPc の変更」、D には「鍵の属性の変更」（Ki / OPc、AMF、SQN、aka-vecgen の加入者は SQN の増加タイプと平文HTTP の許可も）を出す。Ki / OPc は入力したときだけ送り、そのほかは値が変わったときだけ送る（SQN を送らなければ、認証で進んだ SQN に触れない）。「AMF を変更しました。」のように出す。変わった項目がなければ「変更はありません。」。鍵がない加入者は 409「この加入者には鍵がないため、変更できません。加入者を削除してから登録し直してください。」。C が AMF / SQN などを送ってきたら 403。
- C・D には削除のボタンを出す。確認ダイアログに「加入者 … を削除します。認可ポリシーと、鍵の置き場所（…）の Ki / OPc を削除します。よろしいですか？」と出す。削除したら所属の記録も消し、一覧へ移る。所属の記録を消せなかったときは、一覧に「（所属の記録を消せませんでした。下流にない所属の記録として残ります。）」を添える。
- 所属の記録があるのに provisioner にないときは、404「加入者 … は provisioner（本PoC・aka-vecgen）にありません。本BFF の外で削除された可能性があります。所属の記録はシステム管理者が消します。」

### 2.4 停止・再開

- 全員が使える（A・B は自分のテナントのものだけ）。認可ポリシーの状態を変える（`PUT /policies/{imsi}/status`）。停止中の加入者の認証は、鍵の置き場所によらず本PoCが拒否する。効くのは次の認証からで、接続中のセッションは切れない。
- 加入者の詳細と、認可ポリシーの編集画面に置く。一覧にはバッジだけを出す（§17.4 の 5）。
- 表示: 「利用中」と「停止する」のボタン、または「停止中」のバッジと「（認証を拒否します）」と「再開する」のボタン。不正な値は「不明な状態（値）（認証を拒否します。停止または再開で正しい状態に戻せます）」と両方のボタン。認可ポリシーがなければ「認可ポリシーがないため、停止・再開できません（認可ポリシーがない加入者の認証は、もともと拒否されます）。」。認可ポリシーがあるのに状態のない応答（0.2.0 以前の provisioner）では「接続先が停止・再開に対応していません（aka-provisioner 0.3.0 以降と本PoCの provisioning-api 0.4.0 以降で使えます）。」と出し、ボタンを出さない。
- 確認ダイアログ: 「加入者 … を停止します。次の認証から拒否します（接続中のセッションは切れません）。よろしいですか？」「加入者 … を再開します。次の認証から認可ポリシーのルールに従います。よろしいですか？」
- 完了: 「停止しました。次の認証から拒否します（接続中のセッションは切れません）。」「再開しました。次の認証から認可ポリシーのルールに従います。」
- 認可ポリシーが他の操作で削除されていたら 404「IMSI … の認可ポリシーは登録されていません。他の操作（本PoCの Admin TUI など）で削除された可能性があります。」

## 3. 認可ポリシーの編集（`/subscribers/{imsi}/policy`）

- B・C・D（B は自分のテナントのものだけ）。認可ポリシーだけの一覧と、認可ポリシーだけの作成・削除の画面は持たない（§17.4 の 1）。加入者が provisioner になければ 404（§2.3 と同じ）。
- 認可ポリシーがない加入者（食い違い「認可ポリシーがありません」）では「この加入者の認可ポリシーはまだありません。「保存」で作成します。」を出す。既定は deny、ルールなし。
- 入力・ルールの追加・削除・並べ替え・保存・誤りの表示は、既存の BFF の §8.2 と同じ。
  - 既定の動作: deny / allow。
  - ルール: NAS-ID（空白なしの印字可能 ASCII 253 文字まで。`*` はすべて）、許可する SSID（1 行に 1 つ。32 バイトまで。`*` はすべて）、VLAN ID（0〜4094。空なら割り当てない）、Session-Timeout（0〜86400 秒。空か 0 なら送らない）。100 件まで。
  - ルールの追加・削除・並べ替えと既定の動作の切り替えは、フォーム全体を `POST /subscribers/{imsi}/policy/edit` に送り、操作を施した編集欄を返してもらう（provisioner には送らない）。「保存していない変更があります。「保存」で反映します。」を出す。
  - 「保存」で全体を置き換える（`PUT /policies/{imsi}`）。既定の動作が allow のときは、保存の前に確認ダイアログ「既定の動作が allow です。どのルールにも一致しない接続も許可します。保存してよろしいですか？」を出す。成功したら「作成しました。すぐに認可に反映されます。」「保存しました。すぐに認可に反映されます。」。
  - provisioner が返した `invalidParams` は、該当するルールの項目に対応付けて出す。
- 保存済みのものは、上部に状態と停止・再開のボタンを出す（§2.4）。停止・再開では編集中のフォームも一緒に送り、保存していないルールの変更はそのまま残す（保存はしない）。保存（全体の置き換え）では状態は変わらない。
- B には鍵の有無を出さない（§1.2）。C・D には、鍵がなければ「鍵（Ki / OPc）が登録されていません（認可ポリシーだけでは認証できません）」を出す。

## 4. RADIUSクライアント

### 4.1 一覧と登録（`/clients`）

- 全員が一覧を見られる。provisioner の全件を IP アドレスの順に取り、所属で絞る（設計概要 §7.1）。
  - A・B: 自分のテナントのものだけ。
  - C・D: テナントの絞り込み（「すべて」「テナントなし」と各テナント）。各行にテナントの名前を添える。
- 項目: ID、IP アドレス（詳細へのリンク）、名前、ベンダー、テナント（C・D）。
- 所属の記録があるのに provisioner にない ID は、「下流にない」のバッジを付けた行として出す（範囲の中のものだけ）。
- 登録のフォーム（B・C・D）。入力: IP アドレス（IPv4。各数の先頭に 0 を付けない）、共有シークレット（空白なしの印字可能 ASCII 1〜128 文字）、名前（英数字と `_` `-` の 1〜64 文字）、ベンダー（任意。英数字・空白・`-` の 64 文字まで）。C・D は所属のテナント（必須の選択）も選ぶ。B が登録したものは B のテナントに属する。ID は provisioner（本PoC）が採番する。
- 登録したら所属の記録を書き、「RADIUSクライアント …（#ID、IP）を登録しました。」を出す。所属の記録に失敗したときは §2.2 と同じ趣旨の文を出す。
- 同じ IP アドレスが既にあれば 409「その IP アドレスの RADIUSクライアントは既に登録されています（本PoCの Admin TUI など、他の操作で登録された場合もあります）。」（他のテナントのものでも同じ。設計概要 §7）。

### 4.2 詳細（`/clients/{id}`）

- 全員が見られる（A・B は自分のテナントのものだけ）。項目: ID、IP アドレス、名前、ベンダー、テナント（C・D）。
- B・C・D には次を出す。
  - 共有シークレットの表示（ボタン。押したときだけ取得する）
  - 設定の変更: IP アドレス・名前・ベンダー（値が変わったものだけ送る）、共有シークレット（入力したときだけ送る）。「IP アドレス を変更しました。すぐに反映されます。」。変わった項目がなければ「変更はありません。」。他のクライアントが使っている IP アドレスには変えられない（409）。
  - 削除（確認ダイアログ「RADIUSクライアント …（#ID、IP）を削除します。この機器からの RADIUS はすぐに受け付けなくなります。よろしいですか？」）。削除したら所属の記録も消し、一覧へ移る。
- 所属の記録があるのに provisioner にないときは 404（§2.3 と同じ趣旨の文）。

## 5. セッション（`/sessions`）

- 全員が使える。provisioner が中継する本PoCのアクティブセッション（RADIUS の認証で作られ、Accounting-Stop か有効期限で消える）を、接続開始の新しい順に出す。
- A・B: provisioner の一覧（新しい順に 1000 件まで）を取り、自分のテナントの加入者のものだけに絞って、100 件まで出す（設計概要 §15 の 7）。
- C・D: テナントの絞り込み（「すべて」「テナントなし」と各テナント）。「すべて」は provisioner の一覧の新しい 100 件。テナントを選んだときは A・B と同じ作り。各行にテナントの名前を添える。
- `?imsi=`（15 桁）でその加入者のセッションだけを出す（A・B は自分のテナントの加入者だけ。範囲の外なら 404）。形式が違えば 400「IMSI は 15 桁の数字で入力してください。」
- 見出しに件数を出す。100 件を超えるときは「接続開始の新しい 100 件だけを表示しています。」、所属で絞ったときに provisioner のセッションが 1000 件を超えていれば「provisioner のセッションの新しい 1000 件の中から絞り込んでいます。」を出す。
- 項目: 接続開始、IMSI（加入者の詳細へのリンク）、テナント（C・D）、NAS（NAS-Identifier と IP アドレス）、端末の IP アドレス、通信量（入力 / 出力。`1.5 MiB` のように単位をつけ、マウスを重ねると octets の値）、Acct-Session-Id、セッションID。値がないものは `-`。
- 端末の IP アドレス、Acct-Session-Id、通信量は、NAS から Accounting-Request を受けるまで空であることと、有効期限（24 時間。Accounting-Request を受けるたびに延びる）を注記する。
- 読み出しだけで、セッションの切断はできない。

## 6. ダッシュボード（`/`）

- 全員が使える。上部に、自分の範囲の件数を出す。
  - A・B: 加入者（自分のテナントの所属の記録の件数）、停止中、RADIUSクライアント（provisioner の一覧を所属で絞った件数）。
  - C・D: テナントの数、加入者（provisioner の認可ポリシーの件数）、停止中、RADIUSクライアント（provisioner の一覧の件数）。
- 停止中の数は、画面を出した後に htmx で別に読み込む（`GET /dashboard/suspended`）。provisioner の認可ポリシーの一覧（状態つき）を 500 件ずつ、10,000 件まで読み、A・B は所属の記録と突き合わせる。上限で止めたら「（10,000 件までを数えました）」を添える（§17.5 の 5）。
- C・D には、provisioner の状態のカード（§17.3）を出す。未完了の操作があれば、操作の記録へのリンクを添える。
- 「できること」の表（§6.2 を役割で絞ったもの）は下に置き、開閉できるようにする（daisyUI の collapse。CSS だけで開閉する）。
- 件数は、それぞれの一覧へのリンクにする。

## 7. 所属の付け替えと点検（D）

### 7.1 付け替え

- 加入者と RADIUSクライアントの詳細に「所属の変更」を出す（D だけ）。テナント（テナントなしを含む）を選び、確認ダイアログを出してから変える（`POST /subscribers/{imsi}/tenant`、`POST /clients/{id}/tenant`）。
- 加入者と RADIUSクライアントの一覧に、D にだけ行のチェックボックスと「選んだものの所属を変える」を出す（`POST /subscribers/assign`、`POST /clients/assign`）。1 回で加入者は 50 件まで（一覧の 1 ページ分）、RADIUSクライアントは 200 件まで。どの絞り込みでも使え、「テナントなし」の一覧からまとめて割り当てるのにも使う（§17.5 の 1）。
- 付け替える前に、対象が provisioner にあることを確かめる（下流にないものに記録を作らない）。ないものは飛ばす。
- 終わったら元の一覧（詳細からなら詳細）に戻り、「… 件の所属を変更しました。」（飛ばしたものがあれば「… 件は provisioner にないため飛ばしました。」）を出す。変更前と同じテナントのものは数えない。

### 7.2 下流にない所属の記録（`/assignments/orphans`）

- D だけ。本BFF に所属の記録があるのに provisioner にないもの（本BFF の外で削除されたもの）を探す（§17.5 の 2）。
- 加入者: 所属の記録を IMSI の順に読み、provisioner に並行して（同時に 5 件まで）問い合わせる。1 回の表示で 200 件まで調べ、続きは「続きを調べる」で調べ終えた IMSI から再開する（「… 件を調べました（IMSI … まで）」）。provisioner に接続できない・エラーのときは、そこで止めてエラーの文を出す。
- RADIUSクライアント: provisioner の全件と所属の記録の全件を突き合わせる。
- 項目: 種類、IMSI / ID、テナント、記録した日時と操作者。チェックボックスで選び、「選んだ記録を消す」（確認ダイアログ）で消す（`POST /assignments/orphans/delete`）。消す直前に provisioner にないことをもう一度確かめ、あったものは消さずに知らせる（「… 件は provisioner にあったため消しませんでした。」）。

## 8. テナント（D）

- 一覧（`/tenants`）: 名前、加入者・RADIUSクライアント・アカウントの件数（所属の記録とアカウントの数。各一覧の絞り込みへのリンク）、作成日時。作成のフォーム（名前。1〜100 文字。前後の空白は除く）。
- 詳細（`/tenants/{id}`）: 名前の変更、削除（確認ダイアログ）。
- 名前が既にあれば 409「そのテナント名は既に使われています。」
- 所属の記録かアカウントが残っていれば、削除を断る（409「このテナントには加入者 … 件、RADIUSクライアント … 件、アカウント … 件が属しています。先に所属を付け替えるか外し、アカウントを移すか削除してから削除してください。」）。削除しても監査ログは残る。

## 9. アカウント（B・D）

- 一覧（`/accounts`）: メールアドレス、役割、テナント、状態（有効 / 無効）、作成日時と作成者。
  - D: すべて。テナントで絞れる（「すべて」「テナントなし」と各テナント。テナントなしは運用担当とシステム管理者）。
  - B: 自分のテナントのアカウントをすべて出す（テナント管理者を含む）。詳細へのリンクはテナントユーザーにだけ付ける（§17.5 の 7）。
- 作成のフォーム。
  - D: メールアドレス、役割、テナント（テナントユーザー・テナント管理者は必須、運用担当・システム管理者は選ばない）。
  - B: メールアドレスだけ（自分のテナントのテナントユーザーを作る）。
  - メールアドレスは小文字にし、`X-Operator-Id` の形式（英小文字・数字・`.` `_` `-` と `@`、64 文字まで）に合わなければ断る（「メールアドレスは、英数字と . _ - と @ の 64 文字までで入力してください（+ などは使えません）。」。設計概要 §15 の 6）。既にあれば 409。
  - 作成したら「アカウント … を作成しました。Cloudflare Access のポリシーにも、このメールアドレス（またはドメイン）を加えてください。」を出す（Cloudflare の設定は自動化しない。設計概要 §2）。
- 詳細（`/accounts/{id}`）: 役割・テナントの変更（D だけ）、無効化と有効化、削除（確認ダイアログ）。
  - B が扱えるのは自分のテナントのテナントユーザーだけ（設計概要 §15 の 11）。他のテナントのアカウントは 404、自分のテナントのテナント管理者は 403。
  - 最初のシステム管理者（`OSSBSS_INITIAL_ADMIN_EMAIL`）は、削除・無効化・役割やテナントの変更を断り、画面にその旨を出す（「最初のシステム管理者は変更・削除できません（起動のたびにシステム管理者・有効に戻ります）。」）。
  - 自分自身のアカウントも、削除・無効化・役割やテナントの変更を断る（「自分のアカウントは変更・削除できません。」。§17.5 の 4）。
  - 他の操作で変わっていたら（画面を開いた後に役割・テナントが変わった）409「アカウントは他の操作で変更されました。画面を開き直してください。」
- 無効にしたアカウントは、次の要求から 403 になる（設計概要 §5.3）。

## 10. 操作の記録（`/operations`、`/operations/{id}`。C・D）

- 既存の BFF の画面仕様 §11.5 と同じ。一覧は完了していない操作（実行中・やり直し中・失敗）を作成の古い順に 100 件まで、タブで状態を絞る。詳細は手順ごとの状態。完了したものも 7 日間見られる。
- IMSI には、テナントの名前と加入者の詳細へのリンクを添える。
- やり直す・閉じるは D だけ（`Idempotency-Key` つき。閉じるは確認ダイアログ）。C には「やり直しと閉じるは、システム管理者が行います。」を出す。本BFF の監査ログに `operation.retry` / `operation.dismiss` を残す（対象のテナントは IMSI の所属）。

## 11. 監査ログ（`/audit`。B・C・D）

- 本BFF の監査ログ（§1.7）を新しい順に 50 件ずつ出す（「さらに古いものを表示」で続きを読み込む）。項目: 日時、操作者（メールアドレスと役割）、接続元、操作、対象、テナント、内容、トレースID。
  - B: 自分のテナントが対象のものだけ（設計概要 §13）。操作の種類で絞れる。
  - C・D: すべて。テナント（「すべて」「テナントなし」と各テナント）と操作の種類で絞れる（§17.5 の 6）。
- D には、上部のタブで provisioner（`/audit/provisioner`）・provisioning-api（`/audit/prov`）・aka-vecgen（`/audit/aka`）の監査ログも出す（provisioner の中継。既存の BFF の画面仕様 §11.6 と同じ。テナントでは絞れない）。
